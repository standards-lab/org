# Tooling principles

Eleven principles for software that serves an agent, stated for adoption across the workspace.
Each names what it asks, why it holds, and how it shows in practice. Their consumers: the docs
pass (`v1.alignment.docs`) adopts the harness principles (1, 2, 8, 9, 10, 11) into the landing
zone's harness pages and the architecture principles (3 through 7) into the org and architecture
principle pages where the Elemental Architecture does not already state them; the harness tasks
(`v1.harness.hardening`, `v1.harness.sitrep`) and `backlog.harness-tooling` apply them.

## 1. Tools below skills

**Statement.** Tools encode process and guardrails. Skills encode reasoning and behavior.

**Rationale.** Process described in prose is brittle, consumes context, and drifts from what
actually runs. A tool that enforces the process is testable, versioned, and identical every time
it is invoked. The skill that uses it stays short and stays about judgment.

**In practice.**

- Prefer `lint`, `schema`, and `validate` commands over instructions like "the frontmatter must
  contain X."
- The skill says "run the tool, resolve findings." It does not restate what the tool checks.
- If a skill grows a procedural section, that section is a candidate tool.

## 2. Three layers: specification, tooling, skill

**Statement.** Software that serves an agent is layered as specification, tooling, and skill,
bottom to top. Each layer depends only on the one below it.

**Rationale.** A specification scopes a domain; tooling makes the specification operable; a
skill decides when and why to act. Keeping them distinct lets each be replaced or consumed
independently: a non-agent client can use the tooling, and a different agent can use the
specification.

**In practice.**

- A domain is a spec and tools that a skill may sit thinly on top of; it is never "a skill".
- Specifications and tooling are testable without any agent present.

## 3. The schema is the canonical artifact

**Statement.** The schema (JSON Schema or equivalent) is the contract. Code validates against
it; code does not define it.

**Rationale.** A schema is language neutral. Every consumer (a CLI, a plugin, a web app, an
extension, another agent) can validate against the same file without importing the
implementation.

**In practice.**

- Schemas live in a versioned `spec/` directory, one per type or format.
- Structs and types are derived from or validated against schemas; a struct is never the only
  definition.
- Schema changes are versioned and reviewed like API changes.

## 4. Spec repository and instance repository

**Statement.** Anything scaffolded for others is split into a spec repository (schemas, tooling,
adapters, docs) and an instance repository (a person's or team's actual data), generated by the
tooling and pinned to a spec version.

**Rationale.** Copying a personal repository leaks personal data and couples every consumer to
one author's state. Scaffolding produces a clean instance and makes the spec-and-instance
boundary explicit and upgradeable.

**In practice.**

- The go-web-sdk and go-web-sdk-template split is the reference pattern.
- `init` produces an instance; it never copies existing entries.
- An instance records the spec version it targets.

## 5. Providers as adapters, one projection out

**Statement.** External systems are reached through a standard interface per capability with
providers beneath it. The tooling emits a single machine-readable projection of its model for
downstream consumers.

**Rationale.** Adapters isolate vendor churn. A single projection means plugins, UIs, and
extensions consume the model rather than the source format, so the source format can change
without breaking consumers.

**In practice.**

- sqlate's `Dialect`, implemented by its engine sub-modules, is the reference pattern for the
  adapter interface; go-database keeps the pool over the provider and supplies no dialect.
- Downstream consumers read `export` output (JSON); they never parse the authoring format
  directly.
- A new provider is a new adapter, never a change to the interface.

## 6. Declarative, one-way reconciliation by default

**Statement.** For document-driven systems, the authored document is desired state, external
systems are actual state, and the tooling reconciles one way with `plan` and `apply` and
recorded state.

**Rationale.** Bidirectional sync is the largest source of complexity in this class of system
and is rarely needed when the document's author is its only editor. The decision is recorded so
that later features (a UI, collaboration) do not erode it by accident.

**In practice.**

- `plan` shows the diff; `apply` performs it; state is recorded in a state file or back-written
  identifiers.
- Sync is a deliberate, separate decision rather than a feature request.

## 7. A standalone tool alongside the library

**Statement.** A tool is usable with no knowledge of the library's internals; the library is
usable without the tool.

**Rationale.** Established by sqlate. The tool is the operator's interface; the library is the
integrator's. Coupling them forces one audience to carry the other's dependencies.

**In practice.**

- The CLI is a thin consumer of the packages, never the packages' home.
- Both ship from the same repository; both are documented for their audience.

## 8. Extensions call the tooling; they do not reimplement it

**Statement.** A workflow extension (marathon's or another's) invokes the tool's commands. It
never re-encodes the tool's process.

**Rationale.** One process, one place. An extension that reimplements validation or
reconciliation is a second source of truth that will drift.

**In practice.**

- Extension steps map to CLI commands: `lint` before commit, `plan` surfaced for review, `apply`
  as a step.
- If the extension needs behavior the CLI lacks, the CLI gains a command.

## 9. Offload criteria for local or specialized models

**Statement.** Work is offloaded from the frontier agent to a local or specialized model when it
is structured, repetitive, and schema-validated, never because the frontier agent is assumed
weak at it.

**Rationale.** The wins of offloading are cost, locality (an air-gapped fit), and determinism
for fixed transforms. Quality-sensitive generation stays with the stronger model. The offload is
justified on those benefits, since an assumed quality gap does not hold.

**In practice.**

- The mechanism is a tool: a fixed prompt template, an OpenAI-compatible endpoint, and output
  validated against the schema before it is used.
- The frontier agent orchestrates; it never has to touch the generated content.
- Candidates: rollups, reformatting to a template, drafts from a fixed structure.

## 10. Minimal custom code

**Statement.** The custom code in a system is limited to scaffolding, validation, and schema
enforcement. Everything else is configuration, an adapter, or documentation.

**Rationale.** Code that exists to express process is the code that rots. Keeping the surface
small keeps the system maintainable on weekends and adoptable by others.

**In practice.**

- Before adding a command, ask whether it is scaffold, lint, schema, plan, apply, or export. If
  it is none of those, it is probably an adapter or a document.

## 11. Build against a working loop

**Statement.** Design the first slice as one type, one provider, and the full command loop.
Everything else is designed against the loop, never ahead of it.

**Rationale.** Long-term features recorded up front (plugins, UIs, team layers) are constraints
to respect rather than work to start. A working loop exposes which abstractions are real.

**In practice.**

- Record long-term features as constraints on the design. Do not build them until the loop
  runs.
